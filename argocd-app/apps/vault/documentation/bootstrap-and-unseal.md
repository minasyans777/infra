# Bootstrap and unseal runbook

One-time setup for a brand-new Vault cluster (this repo assumes the previous
ad hoc `vault-active.vault.svc.cluster.local` instance is being replaced from
scratch — nothing here migrates existing data). Not run by CI, same as
`registration/scripts/install-cnpg-on-cluster.sh` — this is cluster-prerequisite
work done once, by hand, by whoever operates the cluster.

This is for the current single-node target (`server.ha.replicas: 1`). Once the 2
worker nodes exist, see [scaling-to-ha.md](scaling-to-ha.md) for growing to the
3-node Raft cluster — that's a follow-on to this, not a redo of it.

## 0. Prerequisites

- cert-manager already installed (it's already a `gitops` prerequisite).
- `kubectl` context pointed at the target cluster.
- `helmfile`, `helm`, `terraform` (>=1.9), `vault` CLI installed locally.

## 1. TLS

```
kubectl apply -f tls/00-namespace.yaml
kubectl apply -f tls/10-bootstrap-issuer.yaml
kubectl apply -f tls/20-server-certificate.yaml
kubectl get certificate -n vault vault-server-tls -w   # wait for READY=True
```

## 2. Deploy Vault

```
helmfile apply
kubectl get pods -n vault -w   # wait for vault-0 Running (but NOT Ready — that's expected, it's sealed)
```

## 3. Initialize (once, against vault-0)

```
kubectl exec -n vault vault-0 -- vault operator init \
  -key-shares=5 \
  -key-threshold=3 \
  -format=json > vault-init.json
```

`vault-init.json` now contains **5 unseal key shares and the initial root token**.
This file is the single most sensitive artifact this whole setup produces:

- It is gitignored (`*unseal*.json` in `.gitignore`) — never commit it.
- Immediately split it: give each of 5 key holders exactly one `unseal_keys_b64`
  share (e.g. one line each, pasted into their own password manager entry), then
  delete `vault-init.json` from disk. No single person should hold more than one
  share — the threshold of 3 exists specifically so no individual can unseal alone.
- The root token is for bootstrap only (step 5). Once `terraform apply` has created
  proper policies, revoke it (`vault token revoke <root token>`) rather than leaving
  it around as a standing credential.

## 4. Unseal vault-0

```
kubectl exec -n vault -it vault-0 -- vault operator unseal   # paste share 1, enter
kubectl exec -n vault -it vault-0 -- vault operator unseal   # paste share 2, enter
kubectl exec -n vault -it vault-0 -- vault operator unseal   # paste share 3, enter
```

Confirm it's up as a (single-member) Raft cluster:

```
kubectl exec -n vault vault-0 -- vault operator raft list-peers
```

Whenever this pod restarts (upgrade, crash, node reboot) it comes back sealed and
needs this unseal step repeated — this is the manual toil the task that produced
this repo originally asked to avoid with auto-unseal. See
[architecture.md](architecture.md#why-shamir-instead-of-auto-unseal) for why that
isn't available on this cluster today, and what to do if it becomes available later.
Once there are 3 nodes, every pod needs this repeated independently — Raft peers
replicate data, but each pod seals/unseals on its own; see
[scaling-to-ha.md](scaling-to-ha.md).

## 5. Configure Vault with Terraform

```
cd terraform
export VAULT_ADDR=https://vault.vault.svc.cluster.local:8200   # or a port-forward, see README.md
export VAULT_TOKEN=<the root token from vault-init.json>
export VAULT_CACERT=<path to the CA cert — kubectl get secret -n vault vault-ca-key-pair -o jsonpath='{.data.tls\.crt}' | base64 -d>

terraform init
terraform apply
```

This creates the KV v2 mount, the Kubernetes auth method + `external-secrets` /
`moodle-token-writer` roles, the AppRole auth method + `ci-provisioner` role, and
their policies (see `documentation/architecture.md`).

**After this succeeds, revoke the root token** (`vault token revoke $VAULT_TOKEN`).
Subsequent `terraform apply` runs need a token with a policy capable of managing
mounts/auth/policies — not documented as a fixed recipe here because "who gets an
admin-capable Vault token and how" is an operational decision for whoever runs this,
not something to hardcode. A reasonable option: keep one dedicated `terraform-admin`
policy + periodic-token, generated by hand once via the (about to be revoked) root
token, stored the same way the unseal key shares are.

## 6. Point everything else at it

`gitops/helm/edusystems-org/values.yaml`'s `vault.addr` already points at
`http://vault-active.vault.svc.cluster.local:8200` (**http**, from the old instance).
Update it to `https://vault-active.vault.svc.cluster.local:8200` and make sure
whatever reads it (the moodle-token job) trusts the new CA — mount
`vault-ca-key-pair`'s `tls.crt` the same way `helm/values/vault.yaml` does for the
server pods, and set `VAULT_CACERT` in that job. That edit lives in the `gitops`
repo, not here.
